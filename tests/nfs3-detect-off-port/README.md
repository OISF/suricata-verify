nfs3-detect-off-port
====================

NFSv3 over TCP on port 4040, outside the default NFS port set, a mountd call
on 4041, and a stream that is neither of those on 4042.

From 9.0 the NFS TCP probe is registered as a pattern probe on the to-server
stream, so NFS is detected wherever its calls appear, not only on the
configured ports. This test pins that: the flow is `app_proto: nfs`, its WRITE
and READ produce records with `dest_port 4040`, and the file is extracted.

The mountd flow pins the other half of the claim: a CALL for a different ONC
RPC program must not be claimed as NFS, so that flow stays undetermined and
produces no nfs records. That is also why the probe is to-server only - a
reply carries no program number.

The third flow is the regression guard for how the pattern is anchored. It
opens with `80 00`, the first two bytes of a record marked call, and carries
nothing of an RPC call header, so detection has to finish for it and it must
come out `app_proto: failed`. A pattern that matches and is then refused by
the probe is not concluded on the spot: the flow stays undecided until its
to-server data reaches `pp_max_len`, which is 36 bytes for TCP to-server
(SMB's `MIN_REC_SIZE`). Anchoring the pattern on the record mark rather than
on the call header (message type and rpcvers, offset 8) therefore left every
non-NFS flow shorter than that with no `app_proto` at all.

Generated by `gen.py` (deterministic, no dependencies), raw Ethernet/IPv4/TCP
with checksums zeroed (`-k none`); the client uses ports 50000 to 50002 and
the server 4040 to 4042. NFS data is unique bytes (byte i = i mod 256) over 64
bytes.
