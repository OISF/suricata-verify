nfs3-write-status-code
======================

Two v3 WRITEs whose reply says `NFS3ERR_IO`, one `FILE_SYNC` and one
`UNSTABLE`. A WRITE transaction is settled by its request when the record
carrying the last of the data is complete, and by nothing else; the reply
path has to find the file transaction to record an answer at all, and it does
so through the xid of the last chunk. Both halves of that rule are here.

The `FILE_SYNC` leg (xid 1, `fhA`) is logged while the request is parsed, so
before its reply arrives: its `nfs` record must carry neither `nfs.status`
nor `nfs.status_code`, because `status_code: 0` reads as `NFS3_OK` and would
report a rejected write as a successful one. Its `fileinfo` is written when
the file closes, by which time the reply has landed on the transaction, so
that record says `ERR_IO` with `status_code: 5` - a file the server refused
must not read back as a good file.

The `UNSTABLE` leg (xid 2, `fhB`) is settled by neither record on its own: the
request leaves the transaction open, the reply is parsed into it, and the
record carries `status: ERR_IO` with `status_code: 5`. Before the xid was
recorded for every chunk, a reply to an UNSTABLE write found no transaction,
and a write the server rejected looked exactly like one that was never
answered. Its `fileinfo` is written before that reply reaches the
transaction, so it keeps the default name `OK` and leaves the number out, the
way a file with no reply at all would.

Handles are distinct 32-byte values (`v3_fh(0x41)` / `v3_fh(0x42)`), file data
is 64 bytes of one letter per handle and offsets start at 0.

Generated by `gen.py` (deterministic, no dependencies), raw Ethernet/IPv4/TCP
with checksums zeroed (`-k none`); client 192.168.1.10:941, server
192.168.1.20:2049.
