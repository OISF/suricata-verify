# tls-version-malformed-hello

Pins that `tls.version` does not match a version that was never decoded from a
hello. The pcap carries two flows, both with a ClientHello whose legacy
version field is 0x0303 (TLS 1.2), each followed by an application-data
record:

* flow A (`10.0.2.5 -> 172.16.0.10:443`): the hello's extensions length is
  bogus (0xffff with no extension bytes), so `TLSDecodeHandshakeHello` fails,
  `phase_suppressed` is set and the phase advance is skipped. The
  application-data record then advances the track to the data phase.
* flow B (`10.0.2.6 -> 172.16.0.11:443`): a valid hello (the control).

The decoded test in `DetectTlsVersionMatch` used to be "the track moved past
the hello state" (`client_state > TLS_STATE_CLIENT_HELLO`). Flow A satisfies
that through the application-data record even though its hello never decoded,
so `tls.version:1.2` matched an undecoded flow. The keyword now tracks a
successful hello decode explicitly (the `hello_decoded` connp flag, set only
when the hello including `supported_versions` decoded), so flow A no longer
matches while the valid-hello control still does.

The pcap is generated by `craft-pcap.py`; tshark flags the malformed flow's
extensions length as `Error/Malformed: Vector length 65535 is too large`.
