# Redmine feature 9205

DNP3 link-layer recovery events with `resync-on-bad-start` off (the default).

The capture contains four flows:

1. A valid request and response (baseline).
2. A valid exchange, then octets without a `0x05 0x64` start sequence followed
   by a valid request in the same TCP segment.
3. A valid exchange, then a request with an invalid link-header CRC followed by
   a valid request in the same TCP segment.
4. Octets without a start sequence at the start of the flow, followed by a
   valid request in the same TCP segment.

With the option off, parser behaviour is unchanged: bytes without a start
sequence end DNP3 inspection of the flow (flows 2 and 4 do not log the request
behind them, and `dnp3.bad_start_bytes` is not set). After the bad link CRC in
flow 3 the parser resynchronizes as before; the request it parses behind the
error is marked with `dnp3.policy_divergence`, because a DNP3 endpoint that
stops on link errors would not process it. The baseline flow raises no event.

The same capture is used by `feature-9205-dnp3-recovery-resync` with the option
on. `input.pcap` is generated by `create-pcap.py`.
