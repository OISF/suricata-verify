# DNP3: link header with a valid CRC that breaks a link-layer rule

https://redmine.openinfosecfoundation.org/issues/9432

Eight flows, each one TCP segment that ends in the same valid DIRECT_OPERATE, with a `drop` rule on
`dnp3_func:direct_operate` and `--simulate-ips`. In five of them the segment starts with a 10-octet link header that
has a valid CRC but breaks a link-layer rule (REQUEST_LINK_STATUS or RESET_LINK_STATES with a body, FCV set on
UNCONFIRMED_USER_DATA, a reserved function code) and declares LENGTH 60 or 255. A DNP3 device such as opendnp3
discards such a header when it reads it, resynchronizes on the next start bytes and executes the DIRECT_OPERATE.

Expected: the DIRECT_OPERATE is blocked in all eight flows, and `dnp3.bad_link_rule` is raised once in each of the
five flows with a rule-breaking header and in none of the three controls (no header, and valid REQUEST_LINK_STATUS and
TEST_LINK_STATES headers with LENGTH 5). Before the fix, the parser waited for the declared body and took the
DIRECT_OPERATE as part of it: only the controls were blocked.

`input.pcap` is generated by `create-pcap.py`.
