# Redmine #9190 NFS partial-record reply/RPC/WRITE content errors

Regression test for https://redmine.openinfosecfoundation.org/issues/9190.

## Defect

When an NFS record is delivered partially (the TCP record is larger than the
first parser delivery), Suricata takes a partial-record fast path
(`parse_tcp_partial_data_ts` / `parse_tcp_partial_data_tc`). On the vulnerable
build, several content-validation failures on that path return a fatal
`AppLayerResult::err()`, which disables NFS parsing for the whole flow in both
directions, even though the RPC fragment length (the record boundary) is
already known and the parser could have skipped to the next record.

A *complete* record with the same invalid content is only marked
`malformed_data`, and the parser advances to the next record. Once the record
boundary is known, the partial and complete paths must behave the same.

This test covers the reply-side, RPC-header, and WRITE RPC-level error arms
(NFSv3 WRITE fast path and NFSv4 COMPOUND scan), each with a control flow that
carries an invalid record of the same kind complete, plus a negative control
where the boundary itself is unknown. Two more attack flows (f, g), each with
a control, prove that the skip lands exactly on the record boundary instead of
resynchronising by scanning (see below). A last attack flow (h), with its
control, proves that skipping a malformed partial READ reply also ends its
request, so a later reply reusing the xid is ignored (see below).

## Fixture (`input.pcap`, generated by `make-pcap.py`)

Each flow uses a distinct client source port. Every invalid record claims a
fragment length of 800 (an 804-byte record, at least 512 bytes, so the partial
path is taken when split), except in a-control, whose invalid reply is a short
48-byte complete record, and in d-neg, whose undecodable record marker claims
a fragment length of 16. Every data segment is ACKed by the peer, so Suricata
hands each segment to the parser separately.

Except in d-neg, each invalid record's claimed length ends exactly where the
following record starts, so a fix that skips the unread record tail lands on
the next RPC boundary. The record tails of the a, b, c, e and h flows are
zero filled.
Every file is a single 36-byte READ reply, so no check depends on multi-chunk
file tracking.

## Exact-boundary flows (f, g)

In flows f and g the malformed record is self-consistent except for one field
(`stable = 3`, `eof = 2`): its count and data length cover the rest of the
record, and its data area, which is exactly the unread tail, starts with a
complete, well-formed embedded record (bait) followed by zero filler to the
record end. The embedded records are built with the same helpers as the genuine
ones and parse when they sit on a record boundary. The genuine record follows
the true boundary in the same segment.

- A fix that skips exactly the rest of the record (the record size from the
  marker minus the bytes already delivered) lands on the genuine record and
  never parses the embedded one.
- A parser that resynchronises by scanning for something that looks like an
  RPC record (like the post-GAP `nfs_probe` catch-up), or that resumes right
  after the buffered bytes, parses the embedded record first, then fails on
  the zero filler (fragment length 0) and loses the genuine record.
- Skipping too few or too many bytes also loses the genuine record.

NFS has no sticky buffer for a LOOKUP name, so the LOOKUP alerts (sid 9190202)
are told apart by the `nfs.filename` logged with the alert. The embedded READ
reply has its own marker rule (sid 9190204), and the genuine one too
(sid 9190205; its data also matches the generic sid 9190201, which is only
checked on flows a, b and h). The raw bytes of both embedded records reach the
sensor (sid 9190206).

## Duplicate-xid flows (h)

The complete-record path removes a reply's xid from the request map before it
parses the reply body, so after a malformed READ reply, a later reply reusing
that xid matches no request and is ignored. Skipping a malformed partial READ
reply must end its request the same way. A skip that leaves the request in the
request map takes a later valid reply reusing the xid as the data of the
skipped READ: a file is logged for it and its marker alerts, while the same
records delivered complete (h-control) log nothing for it.

The duplicate reply has its own marker rule (sid 9190207), and its raw bytes
reach the sensor on both flows (sid 9190208). It is followed by a sentinel
reply to a second outstanding READ (generic marker sid 9190201) and by a
LOOKUP, so both directions are shown to still parse records after the
duplicate: it is ignored, not lost to a misplaced skip.

## Fixed expectation

- a-attack, a-control, b-attack, b-control: the READ marker alert
  (sid 9190201) fires and the 36-byte good file is extracted and `CLOSED`
  (fileinfo with the expected sha256).
- c-attack, c-control, e-attack, e-control: the NFS LOOKUP alert
  (sid 9190202) fires.
- f-attack, f-control: sid 9190202 fires for the genuine LOOKUP
  (`nfs.filename` `R9190LOOKUPF`); no alert and no `nfs` record anywhere
  carries the embedded name `R9190EMBEDTS`.
- g-attack, g-control: the genuine marker alert (sid 9190205) fires and the
  36-byte genuine file is extracted and `CLOSED`; the embedded marker alert
  (sid 9190204) never fires and no file with the embedded sha256 is logged.
- f-attack, g-attack: the raw embedded record bytes reach the sensor
  (sid 9190206).
- h-attack, h-control: the duplicate-xid reply is ignored: its marker alert
  (sid 9190207) never fires and no file with its sha256 is logged. The 36-byte
  sentinel file is the only file of each flow, `CLOSED` with the expected
  sha256, and its marker alert (sid 9190201) fires; the LOOKUP alert
  (sid 9190202, `nfs.filename` `R9190LOOKUPH`) fires; the raw duplicate bytes
  reach the sensor (sid 9190208).
- Every attack and control flow records `nfs` `malformed_data` exactly once.
  Flows a, b, c, e, f and g are checked per flow, flows h through a global
  count of 15 over the whole capture (every flow, d-neg included, records it
  once), which does not depend on the packet direction the anomaly is logged
  on.
- d-neg: the NFS LOOKUP is **not** parsed and does not alert; an undecodable
  record marker keeps the fatal behavior, while the raw LOOKUP bytes still
  reach the sensor (sid 9190203).
- Exactly one `app_layer.error.nfs_tcp.parser` over the whole capture, from
  flow d alone.

On the vulnerable baseline the seven attack flows (a, b, c, e, f, g, h) turn
fatal: their marker/LOOKUP alerts are missing, the good files are not
extracted, and the parser-error total is 8 instead of 1. The control and d-neg
flows behave the same on both builds. A fix that skips a malformed partial
READ reply but leaves its request in the request map passes flows a to g, but
fails flow h: the duplicate reply is taken as the data of the skipped READ, so
its marker alerts and its file is logged.

## Regenerate

```
./make-pcap.py
```

timestamps) and writes `input.pcap` in this directory.
