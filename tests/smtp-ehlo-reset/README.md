# Description

A HELO/EHLO issued mid-session must reset the SMTP state exactly as if a
RSET had been issued (RFC 5321 4.1.4). Here the client starts an envelope
as alice, issues an EHLO, then sends a complete message as bob. The EHLO
must abandon alice's envelope so the delivered message is attributed to
bob, its real sender, instead of merging into alice's transaction.

Redmine ticket: https://redmine.openinfosecfoundation.org/issues/8715

# PCAP

The pcap is a live capture of a real Postfix server, generated by the
email sandbox scenario `ehlo-reset` in `smtp-oddseq.py`.

The important sequence is:

```
---> helo client.example.com
<--- 250 mail.example.com
---> mail from:<alice@example.com>
<--- 250 2.1.0 Ok

---> ehlo client.example.com
<--- 250-mail.example.com (multiline)

---> mail from:<bob@example.com>
<--- 250 2.1.0 Ok
---> rcpt to:<alice@example.com>
<--- 250 2.1.5 Ok
---> data
<--- 354 End data with <CR><LF>.<CR><LF>
---> (message body)
---> .
<--- 250 2.0.0 Ok: queued as <id>
---> QUIT
<--- 221 2.0.0 Bye
```

Postfix clears the envelope at the EHLO and delivers the message from
bob. The test checks that Suricata mirrors this: two transactions, the
first holding only alice's abandoned MAIL FROM, the second holding bob's
complete message.
