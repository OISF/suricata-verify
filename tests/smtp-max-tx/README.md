# smtp-max-tx

`app-layer.protocols.smtp.max-tx` documents the maximum number of
*live* transactions per flow, but `SMTPTransactionCreate()`
(`src/app-layer-smtp.c`) rejects new transactions once
`state->tx_cnt > max_tx` -- and `tx_cnt` is a high-water mark that is
never lowered, not even when the detection engine frees old, fully
inspected transactions via `SMTPStateTransactionFree()`.

A single long-lived SMTP connection delivering more than `max-tx`
mail envelopes therefore breaks permanently: the next envelope's
transaction cannot be created, `SMTPProcessRequest()` returns an
error and the app layer is disabled for the whole flow. Later
envelopes are neither parsed, alerted on, nor logged.

## Test

`input.pcap` (generated by `write-pcap.py`, validated against tshark)
holds one SMTP session with **18** mail envelopes back to back; the
live transaction count never exceeds 2. The test runs Suricata with
`max-tx=16`:

- `sid:1` matches every envelope's `MAIL FROM` -- 18 alerts expected.
- `sid:2` matches the **18th envelope (tx id 17)** only.
- `sid:999` is a toclient scaffold (app-layer event) that keeps
  server-reply parsing enabled and must never fire.

## With the bug

The 17th transaction is the last one that can be created
(`tx_cnt` is 16 at creation time, not `> 16`). The 18th envelope's
`MAIL FROM` triggers the failed creation and the parser error:

- `sid:1` alerts 17 times, `sid:2` never.
- 17 `smtp` log events; no event for the 18th envelope.

## Fixed

All 18 envelopes are parsed: 18 alerts for `sid:1`, 1 for `sid:2`,
18 `smtp` log events.
