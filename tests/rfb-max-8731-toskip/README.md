# Test Description

Test that a truncated RFB string does not cause the parser to skip stream
bytes that were already consumed (ticket #8731, PR 16145).

The RFB parser caps the handshake strings (`name`, security failure
`reason`) at `app-layer.protocols.rfb.max-string-length` (here set to 1024).
When a failure reason longer than the cap is fully contained in the current
input buffer, the tail bytes are consumed by the `ok()` result. The parser
must therefore not keep a pending skip for those bytes; otherwise the next
ToClient data is over-skipped (the pending skip was `to_skip` instead of
`to_skip - <tail already in the input>`).

## PCAP

Generated by make_pcap.py. RFB handshake where the server sends:

1. a security-types message with 0 types, followed by a failure reason of
   5000 bytes (cap 1024 => truncated, `rfb.too_long_string`), all in a
   single TCP segment;
2. a well-formed short failure reason (`0123456789`, 10 bytes) in a
   second segment. The state machine re-parses ToClient data in the
   `TCFailureReason` state, so this second reason must be visible to the
   parser and overwrite the transaction's `server_security_failure_reason`.

A parser with the over-skip bug silently drops the second message and logs
the truncated 1024-byte reason instead.

## Checks

- the logged `rfb.server_security_failure_reason` is `0123456789`
  (length 10), proving the second message was not skipped;
- exactly one `rfb.too_long_string` anomaly.
