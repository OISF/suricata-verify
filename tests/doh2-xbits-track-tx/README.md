# Description

`xbits` with `track tx` on a DNS over HTTP/2 (doh2) flow has to address the
transaction the app-layer parser knows - the HTTP/2 transaction - but
detection inspects the DNS transaction that is nested inside it. Before the
fix `DetectXbitTxMatch` passed that inner pointer to the transaction data
getter of the flow application protocol, so the HTTP/2 `tx_data` offset was
applied to a `DNSTransaction`. The result was read as the `txbits` pointer and
dereferenced by `TxBitIsset`: the worker died with SIGSEGV while inspecting
unauthenticated DNS over HTTP/2 traffic.

Redmine #9133.

# PCAP

`input.pcap` is generated by `writepcap.py`, standard library only:

    python3 writepcap.py input.pcap

It carries two cleartext HTTP/2 connections:

  * `10.0.0.1:41111 -> 10.0.0.2:8053`: DNS over HTTP/2 with two transactions
    of their own. Streams 1 and 5 are complete DoH POSTs and responses, which
    is what classifies the flow as `doh2` and gives each transaction a nested
    DNS transaction on each side. Their queries differ (`tx1.example.com` and
    `tx2.example.com`), so a rule can tell the transactions apart. Stream 3 is
    the same POST, but its DATA frame has no END_STREAM, so the DoH to-server
    buffer of the next transaction stays populated. Its length is the value
    the buggy code treats as a pointer, which turns the type confusion into a
    fault instead of a read of the wrong bits. Without a completed request it
    also has no DNS transaction, so no doh2 hook ever runs on it.
  * `10.0.0.1:41112 -> 10.0.0.2:8054`: plain HTTP/2 with two HTML
    transactions, so the test also pins `xbits:track tx` on HTTP/2 itself.

tshark dissects frames 4 and 5 as DoH (HTTP/2 HEADERS plus DATA holding DNS
queries and responses) and frames 11 and 12 as HTTP/2.

# Expected

Two properties are pinned, and they need different rules.

That the bits are found at all: rule 1 sets a transaction bit on the DoH
request, rule 2 reads it back with `xbits:isset,...,track tx` on the doh2
engine of the response. That pair is the crash, and it runs on both
transactions. The other rules cover `isset` of a bit that was never set in
both directions, the `set`/`isset` pair on the to-server side, the same pair
through the http2 engine of the doh2 flow and on the plain HTTP/2 flow, and
`flowint` on the same path. Rules 19 and 20 cross the engines: 19 reads
through the http2 engine the bit rule 1 set through the doh2 engine, 20 reads
through the doh2 engine the bit rule 9 set through the http2 engine. Both
alert, because either engine addresses the bits of the HTTP/2 transaction the
parser knows; a fix that resolved the bits from the transaction handed to the
engine (the DNS transaction for doh2) would keep the two apart.

That the bits are stored per transaction and not per flow: rules 13 to 18 set
a bit on one transaction, read it back on that same transaction and read it
from the other one. The read on the transaction that set it alerts (14 and
17), the read from the other one does not (15 and 18). A store keyed by flow
rather than by transaction would alert on 15 and 18 and fail the test, and the
alerting counterparts 14 and 17 keep that verdict from being the trivial one
of a hook that never ran. The DNS buffers these rules match on are only
available once the side they describe is complete, so they sit on
`request_closed` and `response_closed`; a rule that pairs a DNS buffer with a
`*_started` hook is refused when the ruleset loads.

`xbits:unset`, `xbits:isnotset` and `xbits:toggle` cannot reach this path:
`track tx` with anything but `set` or `isset` is rejected when the rule is
parsed.
