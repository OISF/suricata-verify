Lua SMTP cached-handle liveness, logger context
===============================================

The same stale-handle contract as `tests/lua/lua-smtp-stale-tx`,
exercised through a different attachment mechanism: the script is
a **lua output** script, so the cached handle is read from
`log()` - the per-transaction logger callback - not from a
detection rule's `match()`. The two mechanisms are both legitimate
and are not interchangeable; do not "fix" one into the other.

The capture carries two complete transactions in one session. The
script caches the handle of the first logged transaction and reads
it from the second's log call: by then the parser has freed the
first one (the second `MAIL FROM` opened the next transaction), so
the accessor must fail closed - the read raises, `log()` errors,
and the engine logs "tx no longer valid", which the shell check
asserts positively. Red on the unfixed engine, where the read
dereferences the freed transaction and completes silently.

What a green proves and does not: it proves the accessor **failed
closed** on a stale handle - a currentness-style guard (the handle
is not the transaction under inspection) would log the same string
and pass. The use-after-free evidence itself is the asan leg of the
CI matrix, where the unfixed engine dereferences freed memory
instead of logging nothing. The tx_id 0/1
event filters make the two-transaction premise of the capture
visible.

`input.pcap` is generated by `gen_input_pcap.py` (scapy) and
committed; the script is kept for provenance and is not run from
the test (the CI image has no scapy/tshark, and a setup failure
scores the test as failed).
