# Redmine #8818 IPv4 defrag total-length overflow

Regression test for the analogous IPv4 case discovered while fixing
https://redmine.openinfosecfoundation.org/issues/8818.

The pcap is generated by `make-pcap.py` with Scapy. It contains one IPv4 UDP
datagram split across 46 fragments. The first fragment has a 60-byte IPv4
header containing 40 bytes of options, while the fragmentable portion ends at
byte 65,515. Reassembly would therefore produce a 65,575-byte IPv4 packet, 40
bytes beyond the 16-bit IPv4 total-length limit.

Vulnerable builds validate the fragmentable portion using the minimum 20-byte
IPv4 header, then add the actual 60-byte header during reassembly. The total
length wraps to 39 when stored in the 16-bit IPv4 total-length field, and the
rebuilt UDP datagram bypasses protocol and content inspection.

A fixed build rejects the oversized reassembly, raises
`ipv4.frag_pkt_too_large` on the final fragment, and does not count the chain as
reassembled.

PCAP SHA256: `e18cc1efab1a10919efa6ddeff060c075b06df712922e786f9cc177ce1d369da`.
