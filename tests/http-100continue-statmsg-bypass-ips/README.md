# http-100continue-statmsg-bypass-ips

IPS-mode reproducer for the 100-Continue deviation on the
`http.stat_msg` buffer: on a 100-continue exchange the parser rewinds the
response tx in place and the detection engine's per-tx state is left
stale, so the final 200's reason phrase is never inspected (false
negative) and the 100 line's reason phrase double-alerts (false
positive). `http.stat_msg` is affected because it registers the same
LINE response progress as `http.stat_code` and shares the per-tx
`detect_progress` bookkeeping that the 100 line's final run stores;
the reason phrase buffer is also left stale by the rewind.

## Expected results (flow B, `10.0.0.3`)

| observation | flow A | flow B (expected) | on a pre-fix build |
|---|---|---|---|
| `http.stat_msg; content:OK` on the final 200 (sid 1102) | 1 (sid 1101) | 1 | **0 (bypassed)** |
| `http.stat_msg; content:Continue` on the 100 line (sid 1103) | 0 | 1 | **2 (double alert)** |
| http log status for the final response | 200 | 200 | 200 |

The test is RED against a pre-fix build on exactly the two flow-B
checks and GREEN once the fix (new response tx / progress reset on
100-continue) lands.

## Traffic

Same standard, spec-compliant A/B exchange as the sibling test
`http-100continue-statcode-bypass-ips`:
flow A is a normal `GET -> 200` baseline; flow B is a `POST` with
`Expect: 100-continue` (RFC 7231), a bare `100 Continue` and a final
`200 OK` - legitimate client and server, reachable in ordinary
traffic. in IPS mode the stream engine parses each packet's own direction immediately, so the exchange reproduces the deviation with no ACK dependency.

## Notes

- `input.pcap` is byte-identical to the sibling test's pcap
  (scapy-generated by `writepcap.py`).
- tshark dissects the pcap as HTTP overall; flow B's request and
  100-line packets are not HTTP-dissected by tshark (4.6.4) because
  the 100 response spans two packets - dissector quirk, see the
  sibling test's notes. Suricata parses the pcap correctly, as the
  test results show.
