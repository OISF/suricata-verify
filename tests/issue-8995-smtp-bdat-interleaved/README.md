# Description

Two valid BDAT chunks are pipelined. The first chunk is complete and the
second chunk is only partially received when the server rejects the first.
Suricata must not clear the global BDAT data mode for the earlier reply,
because the mode and chunk counters describe the later chunk.

After the second chunk is drained and rejected, RSET abandons transaction 0.
A message delivered with DATA in transaction 1 contains an EICAR marker; its
alert proves that the interleaved rejection did not desynchronize subsequent
SMTP and file inspection.

Redmine ticket: https://redmine.openinfosecfoundation.org/issues/8995

# PCAP

The pcap is generated by `writepcap.py`. It is synthetic because the error
reply must be interleaved while the second chunk is only partially visible on
the client stream.

The important sequence is:

```
<--- 220 mail.example.com ESMTP ready
---> EHLO client.example.com
<--- 250-PIPELINING
<--- 250 CHUNKING

---> MAIL FROM:<first@example.com>
<--- 250 2.1.0 Ok
---> RCPT TO:<discard@example.com>
<--- 250 2.1.5 Ok

---> BDAT 4
---> ABCD
---> BDAT 10 LAST
---> 12345
<--- 451 4.3.0 First chunk rejected
---> 67890
<--- 503 5.5.1 Transaction failed
---> RSET
<--- 250 2.0.0 Reset state

---> MAIL FROM:<alice@example.com>
<--- 250 2.1.0 Ok
---> RCPT TO:<bob@example.com>
<--- 250 2.1.5 Ok
---> DATA
<--- 354 End data with <CR><LF>.<CR><LF>
---> (message containing the EICAR test string)
---> .
<--- 250 2.0.0 Queued
```

An unconditional clear on the first `451` makes the remaining `67890` wait in
the command-line buffer and merge with `RSET` as `67890RSET`. Transaction 0 is
then not reset, so the delivered message does not receive transaction 1 and
the checks fail.
