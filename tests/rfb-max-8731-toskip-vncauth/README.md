# Test Description

Test that a truncated RFB string does not cause the parser to skip stream
bytes that were already consumed (ticket #8731, PR 16145).

Sibling of `rfb-max-8731-toskip`, but drives the parser into the
`TCFailureReason` state through the spec-compliant VNC authentication
failure path (RFB 3.8, security type 2), so the handshake is fully
dissectable by tshark's VNC dissector. The over-skip condition is the
same as in the sibling test: the failure reason longer than
`app-layer.protocols.rfb.max-string-length` (here set to 1024) is fully
contained in the current input buffer, so its tail is consumed by the
parser's `ok()` result; the pending skip must not also account for the
bytes already in the input, or the next ToClient data is over-skipped.

## PCAP

Generated by make_pcap.py. RFB 3.8 handshake where the server sends:

1. one security type (VNC auth, 2); the client selects it; a 16-byte
   challenge and 16-byte response complete the VNC authentication;
2. a security result of `1` (failure), sent as a 4-byte big-endian
   value — the layout both dissectors model: Suricata's parser reads it
   with `be_u32` and tshark's VNC dissector with `tvb_get_ntohl`
   (packet-vnc.c, VNC_SESSION_STATE_SECURITY_RESULT);
3. a failure reason of 5000 bytes (cap 1024 ⇒ truncated,
   `rfb.too_long_string`) in the SAME segment as the result;
4. a well-formed short failure reason (`0123456789`, 10 bytes) in a
   second segment. The state machine re-parses ToClient data in the
   `TCFailureReason` state, so this second reason must be visible to
   the parser and overwrite the transaction's
   `server_security_failure_reason`.

A parser with the over-skip bug silently drops the second message and
logs the truncated 1024-byte reason instead.

## tshark validation

The handshake segments are dissected as VNC: both protocol versions,
`num_security_types: 1`, `security_type: 2`, `client_security_type: 2`,
the 16-byte `auth_challenge` and `auth_response`, and for the result
segment: `Authentication result: Failed`, `Length of authentication
error: 5000` and the 5000-byte `Authentication error`. The 14-byte
second-reason segment is re-dissected as a `vnc.auth_result` field; a
re-sent failure reason is a test-specific construct (a real server
closes the connection after the first failure reason), so no dissector
can validate that segment — the payload is still never left as
undecoded data.

## Checks

Same as `rfb-max-8731-toskip`:

- the logged `rfb.server_security_failure_reason` is `0123456789`
  (length 10), proving the second message was not skipped;
- exactly one `rfb.too_long_string` anomaly.
