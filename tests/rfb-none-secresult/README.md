# Test Description

Test that the RFB parser consumes the security result on the "None"
(security type 1) path.

The parser's `TSSecurityTypeSelection` branch routes a client selection
of type 1 ("None") directly to `TSClientInit` (the client's 1-byte
shared flag), skipping the security result that an RFB 3.8 server sends
after the selection (0 = OK, 1 = failure + reason string). tshark's
VNC dissector models the spec the same way: for a client version >= 3.8,
a "None" selection is followed by a security result
(`VNC_SESSION_STATE_SECURITY_RESULT` in packet-vnc.c), not by the
client init.

With the result bytes unconsumed, they arrive on ToClient while the
state machine is in `TSClientInit` — a ToServer-only state. The
"Invalid state for response" catch-all fires, a `confused_state`
anomaly is logged and the parser switches to `Skip`, discarding the
shared flag and the whole ServerInit. The transaction is then logged
with only the protocol versions and the chosen security type.

## PCAP

Generated by make_pcap.py. RFB 3.8 handshake, security type 1 ("None"):

1. `RFB 003.008` version exchange;
2. server offers one security type (None, 1); client selects it;
3. security result: 4-byte big-endian `0` (OK). The 4-byte width is the
   layout both dissectors model: the parser's `be_u32`
   (`parse_security_result`) and tshark's VNC dissector
   (`tvb_get_ntohl`). The original rfbproto text is generally quoted as
   a 1-byte result; confirm the intended width when fixing (see
   Related issues);
4. client init: shared flag = 1;
5. server init: 1920x1080, 32bpp true colour, name "test";
6. clean TCP close (EOF) so the transaction is logged.

## tshark validation

The pcap is fully dissected as VNC: both protocol versions,
`num_security_types: 1`, `security_type: 1` (None),
`client_security_type: 1`, `Authentication result: OK`, the
`Share desktop flag`, and the ServerInit (width/height/pixel format/
name). No undecoded data.

## Checks

- exactly one `rfb` event with `security_type: 1`,
  `security_result: OK`, `screen_shared: true` and the ServerInit
  fields (`framebuffer` 1920x1080, name "test") — this set of fields is
  only present when the handshake was parsed end to end;
- zero `anomaly` events of type `confused_state`.

Against a parser with the bug, the first check matches 0 events and the
second matches 1 (the logged `rfb` event contains only the versions and
`security_type`).
