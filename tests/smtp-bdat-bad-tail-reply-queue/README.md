# Description

SMTP BDAT (CHUNKING) with a malformed argument (`BDAT 5 X`) rejected by a
server that keeps the session open. The rejected command must still occupy
a slot in the reply queue: the client pipelines MAIL FROM, RCPT TO and
DATA behind the malformed command in a single segment, and the server
answers everything in order. Only if the 501 rejection is consumed by the
BDAT slot is the 354 matched to DATA and data mode entered; a missing
slot shifts every following reply, RCPT TO's 250 lands on DATA
(DATA_COMMAND_REJECTED) and the message body is parsed as commands
instead of being inspected.

The companion test smtp-bdat-bad-tail-next-mail covers the parser
surviving the rejection, but its Postfix server closes the session after
the 521 so no later replies exist to expose a missing queue slot.

Redmine ticket: https://redmine.openinfosecfoundation.org/issues/8741

# PCAP

The pcap is generated by writepcap.py. A real Postfix server cannot
produce this dialog (it rejects malformed BDAT with a 521 and closes),
so the capture is synthetic: the server rejects with 501 and continues,
as other MTAs do. The server does not advertise PIPELINING, so entering
data mode depends on matching the 354 reply to the DATA command rather
than the pipelined-server shortcut.

```
<--- 220 mail.example.com ESMTP
---> EHLO client.example.com
<--- 250-mail.example.com
<--- 250-8BITMIME
<--- 250 CHUNKING

---> BDAT 5 X
---> MAIL FROM:<alice@example.com>
---> RCPT TO:<bob@example.com>
---> DATA

<--- 501 5.5.4 Syntax: BDAT count [LAST]
<--- 250 2.1.0 Ok
<--- 250 2.1.5 Ok
<--- 354 End data with <CR><LF>.<CR><LF>

---> (message body)
---> .
<--- 250 2.0.0 Ok: queued as ABCDEF
---> QUIT
<--- 221 2.0.0 Bye
```

The test checks that the message pipelined behind the rejected command is
logged as one transaction with both its SMTP envelope and its parsed
email body (PARSE_DONE), that the rejected command raises INVALID_BDAT,
and that no DATA_COMMAND_REJECTED is raised, which would indicate a
shifted reply queue.
