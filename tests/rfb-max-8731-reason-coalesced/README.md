# Test Description

Regression test for the `TCFailureReason` rem-handling defect of
ticket #8731 (present in PR 16145/16159/16163/16164 as merged so far):
a second, well-formed failure-reason PDU that is coalesced in the SAME
TCP segment as a truncated (longer-than-cap) first failure reason is
silently dropped.

The `TCFailureReason` branch does:

    if request.to_skip >= rem.len() as u32 {
        self.to_skip_tc = request.to_skip - rem.len() as u32;
    }
    ...
    return AppLayerResult::ok();     // rem is never processed

The framework treats `ok` as full-input-consumed
(`app-layer-parser.c`: `consumed = input_len`), so the bytes left in
`rem` (a following PDU) are dropped, and when `to_skip < rem.len()`
the guard leaves `to_skip_tc` untouched while the pending skip is
effectively mis-credited by the rem bytes — the rem bytes are not part
of the skipped string tail. The parser stays in the `TCFailureReason`
state and re-parses following reason PDUs (last reason wins — pinned
by the sibling test `rfb-max-8731-toskip-vncauth`, where the second
reason arrives in a separate segment and is parsed). The correct
handling consumes the in-buffer part of the string tail, credits only
the not-yet-buffered part to `to_skip_tc`, and continues the state
loop with the remaining bytes.

## PCAP

Generated by make_pcap.py. RFB 3.8 handshake, security type 2 (VNC
auth — spec-compliant path, independent of the separate None-path
security-result issue): version exchange, 1 security type (VNC auth)
offered and selected, 16-byte challenge / 16-byte response, then ONE
server segment containing:

- security result: failure (1), 4-byte big-endian — the width modeled
  by both the parser's `be_u32` and tshark's VNC dissector;
- first failure reason: 2048 bytes of 'A' (> cap 1024 set in
  test.yaml): truncated, `rfb.too_long_string`;
- second failure reason: 10 bytes "0123456789", well-formed — must be
  parsed (last reason wins).

A real server `write()` of the reason plus a follow-up produces
exactly this coalesced shape. Clean TCP close (EOF) so the
transaction is logged.

## tshark validation

The pcap is dissected as VNC: both protocol versions,
`num_security_types: 1`, `security_type: 2`, `client_security_type: 2`,
`auth_challenge` / `auth_response`, `Authentication result: Failed`,
`Authentication failure reason` (length 2048 and the string). No
payload is left as undecoded data before the failure reason.

## Checks

- exactly one `rfb` event with the VNC-auth failure handshake
  (`security_type: 2`; the `security_result` field is absent on the
  failure path - pre-existing parser behaviour, status 0 only) and the
  SECOND reason logged (`server_security_failure_reason: 0123456789`,
  `__len: 10`) — against v3.4-v3.6 the logged reason is the truncated
  first reason (1024 × 'A') and the second PDU is lost;
- exactly one `rfb.too_long_string` anomaly (the truncated first
  reason);
- no `confused_state` / `malformed_message` anomalies.
