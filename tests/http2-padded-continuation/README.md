# Description

Test http2 reassembly of PADDED header blocks split over CONTINUATION
frames.

https://redmine.openinfosecfoundation.org/issues/8840

A PADDED header frame carries its padding inside the first physical
frame: `[Pad Length][Priority?][first fragment part][Padding]` (RFC 9113
6.2.3 field layout; the nghttp2 sender arranges the padding "so that it
is included in the first frame completely"). CONTINUATION frames carry
only field block fragment bytes.

input.pcap has two HTTP/2 connections, each with a 165-byte response
field block split over HEADERS + 2x CONTINUATION:

- c1 (port 443): PADDED split response.
- c2 (port 444): PADDED split response + PADDED + PRIORITY single-frame
  request (PRIORITY on the request side: `http.http2.response` has no
  `priority` property in `etc/schema.json`, so a PRIORITY response HEADERS
  frame fails eve schema validation).

The marker header (`x-splitpad`) is the last field of the block, in the
final CONTINUATION fragment: it is only decoded when the Pad Length
field, the priority fields and the trailing padding are all handled
correctly during reassembly.

# PCAP

Generated by gen_pcap.py (scapy), regular pcap.

Validated with tshark: both connections dissect as
`SETTINGS[0], HEADERS[1]: 200 OK, CONTINUATION[1], CONTINUATION[1]` and
the full header section (including `x-splitpad`) decodes:

    tshark -r input.pcap -d tcp.port==443,http2 -d tcp.port==444,http2 -V
