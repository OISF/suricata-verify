# nfs4-open-partial-write

An NFSv4 `OPEN` op with a `CLAIM4_DELEGATE_CUR` claim leads a `WRITE` whose
count runs far past the end of the record. The RPC record claims 8188 bytes and
all 8192 arrive, so this is a *complete* record: the partial-record scanner gets
the first 4 KiB packet only, and the full compound parser gets the finished
record.

`OPEN4args` is parsed per the wire (RFC 8881 18.16.1), union-aware, so the parse
now reaches the `WRITE` op instead of rejecting an un-mirrored claim. It fails
there: the claim's `component4` writes 7 name bytes under a declared length of 5,
so the op walk (parser and its mirrored scanner alike) lands 3 bytes inside the
following `WRITE` op code, and the 17 MiB count is never seen as a count.

What the test guards is that such a record is not dropped in silence. A failed
parse of a complete record runs the same bounded scan the partial path uses over
the very bytes the parser was given, and rejects the record with exactly one tx:

- `Oversized` (a WRITE claim above `nfs.max-write-size`) -> `write_request_too_large`
- anything else (`Incomplete`, `Clean`, `Malformed`) -> `malformed_data`

The scan is `Clean` here, so this record logs one `malformed_data` tx. Before
that reject existed the record was consumed with no tx and no event at all: the
error arm only called `set_event`, which labels the most recent transaction and
does nothing when the state has none.

The record is fed over two 4 KiB packets with the server acked in between, so the
first packet is scanned on its own and the second completes the record. By
construction the parser never buffers toward the 17 MiB claim (Redmine #8791).
