# Redmine #9188 NFS zero-count partial records: exact record boundary

Regression test for https://redmine.openinfosecfoundation.org/issues/9188
(stable backport https://redmine.openinfosecfoundation.org/issues/9225),
covering both directions.

## Defect

An NFSv3 WRITE call or READ reply with `count = 0` has no file data, but its
RPC record can still be longer than its header. When such a record is 512
bytes or larger and its first parser delivery is incomplete, it takes the NFS
TCP partial-record fast path (`parse_tcp_partial_data_ts` for a WRITE,
`parse_tcp_partial_data_tc` for a READ reply). `process_write_record` and
`process_read_record` returned early on a zero count, without skipping the
unread tail of the record, while the fast path reported the whole input as
consumed. The next delivery was then parsed as a new RPC record: a record
embedded in the tail was parsed, and the zero filler after it failed as an
RPC header, which disables NFS parsing for the flow in both directions.

The fix skips the rest of the record, as the complete-record path does with
the same bytes, and, for a READ reply, ends its request like a complete reply
does.

## Fixture

`input.pcap` is generated by `make-pcap.py` (scapy, deterministic). Every
flow ends with a REMOVE call; the to-client flows first send the READ calls
the replies answer. Zero-count records are 804 bytes unless noted.

| Flow | Src port | Shape |
| --- | --- | --- |
| w-attack | 3101 | NULL; zero-count WRITE split after its 76-byte header; then its tail, starting with an embedded LOOKUP (`R9188BAIT-TS`), plus the REMOVE. |
| w-control | 3102 | Same bytes, the WRITE record complete. |
| w-consecutive | 3103 | The first delivery holds the header and 24 bytes of the tail; the next segment completes the record and holds the header of a second zero-count WRITE, partial mid-segment. |
| w-multiseg | 3104 | A 4004-byte zero-count WRITE whose tail spans three segments. |
| w-gap | 3105 | As w-attack, but the first 300 bytes of the tail are lost (stream gap) and the embedded LOOKUP follows the gap. |
| r-attack | 3106 | Zero-count READ reply with attributes split after its 132-byte header; then its tail, starting with an embedded reply (`R9188BAIT-TC`) to an outstanding READ, plus the genuine reply (`R9188MARK-R`). |
| r-control | 3107 | Same bytes, the reply record complete. |
| r-dupxid | 3108 | Zero-count READ reply without attributes, first 140 bytes, then the rest; a valid reply reusing its xid (`R9188DUPXID`); the reply to a second READ (`R9188MARK-D`). |
| r-dupxid-ctl | 3109 | Same bytes, the reply record complete. |
| r-consecutive | 3110 | Two zero-count READ replies; the second (4004 bytes) starts mid-segment and its tail spans three segments; then the genuine reply (`R9188MARK-E`). |
| z-short | 3111 | Ordinary short, complete zero-count WRITE and READ reply, then a genuine reply (`R9188MARK-Z`). Unaffected. |

## Fixed expectation

- The REMOVE alert (sid 9188101) fires on all 11 flows. On the vulnerable
  build it fires only on the control flows 3102, 3107, 3109 and 3111.
- Records embedded in a skipped tail are never parsed: no LOOKUP alert (sid
  9188102) and no embedded READ data alert (sid 9188105), so the skip lands
  exactly on the record boundary rather than resyncing on something that
  looks like a record. Raw-TCP rules show the embedded bytes reach the
  sensor. The vulnerable build parses the embedded records of 3101, 3105 and
  3106.
- The reply reusing the xid of the zero-count reply is ignored (no sid
  9188106), as on the complete path.
- The genuine READ data alerts (sid 9188104) on all six to-client flows, and
  exactly the six genuine files are extracted, CLOSED, with their sha256.
- No NFS anomaly, no `app_layer.error.nfs_tcp.parser` (7 on the vulnerable
  build), and the w-gap flow has its stream gap (`tcp.reassembly_gap: 1`).
