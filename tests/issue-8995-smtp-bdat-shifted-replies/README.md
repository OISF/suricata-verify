# Description

An early-rejecting server and Suricata disagree about whether a BDAT chunk's
advertised octets were consumed. Suricata treats 17 octets as chunk data and
queues a later `BDAT 1000000`; the server treats those same octets as a
MAIL FROM command. The server's replies are therefore shifted relative to
Suricata's command queue.

The first `503` belongs to an earlier, non-current BDAT and must not clear the
later chunk's data mode. The following `250` is matched to the current
queue-tail BDAT while its million-octet payload is still missing. Any reply to
an in-progress BDAT means the server is no longer waiting for that payload, so
Suricata must clear data mode even though the shifted reply is successful.

RSET then abandons transaction 0. A message delivered with DATA in transaction
1 contains an EICAR marker; its alert proves that shifted replies did not leave
subsequent SMTP and file inspection desynchronized.

Redmine ticket: https://redmine.openinfosecfoundation.org/issues/8995

# PCAP

The pcap is generated by `writepcap.py`. It is synthetic because it models an
early-rejecting server that does not drain the advertised chunk before parsing
later client bytes as commands.

The important sequence is:

```
<--- 220 mail.example.com ESMTP ready
---> EHLO client.example.com
<--- 250-PIPELINING
<--- 250 CHUNKING

---> BDAT 17
---> MAIL FROM:<a@b>             (chunk data to Suricata; command to server)
---> BDAT 1000000
<--- 503 5.5.1 Need RCPT command  (first BDAT)
<--- 250 2.1.0 Ok                (MAIL FROM; mapped to current BDAT)
<--- 503 5.5.1 Need RCPT command  (large BDAT; unmatched by Suricata)
---> RSET
<--- 250 2.0.0 Reset state

---> MAIL FROM:<alice@example.com>
<--- 250 2.1.0 Ok
---> RCPT TO:<bob@example.com>
<--- 250 2.1.5 Ok
---> DATA
<--- 354 End data with <CR><LF>.<CR><LF>
---> (message containing the EICAR test string)
---> .
<--- 250 2.0.0 Queued
```

An error-only queue-tail guard ignores the earlier `503`, accepts the shifted
`250` without leaving data mode, and cannot associate the final `503` with a
queued command. RSET and the delivered message are then consumed as part of
the missing million-octet chunk and the checks fail.
