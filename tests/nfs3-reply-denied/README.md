NFSv3 flows carrying an RPC `MSG_DENIED` reply (RFC 5531 9): 20 bytes, no
verifier, no `accept_stat`, no program body.

Four flows, each server segment ACKed by the client so the to-client data is
parsed segment by segment as on a live link:

- A: two WRITE chunks, chunk 1 answered by a denial, chunk 2 with an OK;
- B: the same with the replies reversed;
- C: a READ answered by a denial only;
- D: not RFC traffic — a denied record that claims a 600 byte READ reply body,
  delivered as a 200 byte segment and the rest.

The checks pin what a denial does to the status: `rpc.status` reports `DENIED`
whatever the order of the replies, `nfs.status` keeps the first NFS status it
saw, a READ denial leaves no NFS status, and flow D raises `malformed_data` and
reconstructs no file. Without the deny handling the parsing fails, the record
is reported as malformed and the rest of the direction is lost.

A flow whose first to-client segment is a denial still gets
`APPLAYER_DETECT_PROTOCOL_ONLY_ONE_DIRECTION`: the protocol probe wants an
accepted reply, and a denial carries no program number. Parsing continues, so
nothing is lost; the anomaly is not pinned here.

`input.pcap` is generated by `gen.py` and carries zeroed checksums, hence
`-k none` in the test args.
