Test that a transactional (`=>`) rule works on HTTP/2, i.e. on a protocol
whose buffers are matched by the HTTP/2 parser rather than by libhtp
(Redmine #9087). Every other `=>` test in this directory is HTTP/1; the
engine list under test here is the per-transaction, per-direction engine
list of an HTTP/2 transaction.

One HTTP/2 stream carries a single transaction: `POST /upload` with a 6 byte
body, answered by `200`. The rules put one HTTP/2 buffer in each direction
of that same transaction: `http.uri`/`http.request_body` toserver,
`http.stat_code`/`http.stat_msg` toclient. The test runs with
`--simulate-ips` so both directions are inspected as they arrive:

- packet 6: `HEADERS[1]` - `http.uri` matches, the toserver engines run
- packet 7: `DATA[1]` + END_STREAM - `http.request_body` matches, the
  request is complete
- packet 8: `HEADERS[1]` `:status 200` + END_STREAM - `http.stat_code`
  matches and the pair closes

Rules:

- sid 1 and sid 2 have a toclient half that cannot match, so they must stay
  silent. sid 1 is the guard that matters: it alerts on the request alone on
  `7ad9874c0` (1 alert at packet 7) and is silent with the fix. Its
  toclient condition is `http.stat_msg`, which HTTP/2 leaves empty (there
  is no reason phrase), and that is what puts the toclient engine in the
  middle of the progress order instead of last.
- sid 2 is the minimal shape the maintainer asked for - exactly one buffer
  per direction, `http.uri` against `http.stat_code: 404`. Here the
  toclient engine is last, so even `7ad9874c0` waits for it: this one is
  silent on all three builds and pins the shape itself.
- sid 3 and sid 4 are the pairs whose halves both match. They alert exactly
  once, at the response, on every build including main: the pair requirement
  costs no HTTP/2 alert in this ordering.
- sids 21 and 22 are a plain `flow:established` flowbit pair over the same
  two buffers, proving the toserver and toclient halves really do match on
  this transaction.

This test uses the ordinary request-then-response order. The response-first
ordering, where the pair does not close and HTTP/1 documents the false
negative, is not covered for HTTP/2 here.

Alert counts per sid, measured on built binaries:

| build | sid 1 | sid 2 | sid 3 | sid 4 | sid 22 |
|---|---|---|---|---|---|
| main `7ad9874c0` | 1@7 | 0 | 1@8 | 1@8 | 1@8 |
| `c4c778035` alone | 0 | 0 | 1@8 | 1@8 | 1@8 |
| `c4c778035` + `a4f2c2486` | 0 | 0 | 1@8 | 1@8 | 1@8 |

`input.pcap` is generated by `gen_input_pcap.py` next to it; it is regular
libpcap and `tshark -d tcp.port==80,http2 -Y http2` decodes the SETTINGS,
HEADERS and DATA frames named above.
