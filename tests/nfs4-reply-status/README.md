Two NFSv4 reply-status cases that a compound can produce.

**Flow A** - `PUTFH, WRITE, GETATTR`, answered `WRITE=NFS4_OK` followed by
`GETATTR=NFS4ERR_IO`. The compound opens a WRITE file transaction, and a
trailing operation must not replace the write's own result: the record reports
`nfs.status: OK`. Selecting the last significant op for the status made an
UNSTABLE write log as failed.

**Flow B** - a successful exchange, then a `CLOSE` answered `MSG_ACCEPTED` with
`accept_stat GARBAGE_ARGS`. That reply is well formed but carries no NFS
COMPOUND result, so the transaction has to finish with no NFS status. Before
the body-less reply handling the empty body was parsed as a compound, which
raised `malformed_data` and left the request transaction open until eviction.

**Flow C** - `PUTFH, READ, GETATTR`, answered `READ=NFS4_OK` and
`GETATTR=NFS4ERR_IO`: the READ result is what its transaction reports.

**Flow D** - a v3 call answered `PROG_MISMATCH`, the one accept_stat that
carries a body (the version range). Those eight bytes must be consumed with the
header, not read as NFS data: the flow stays NFS and nothing is flagged
`malformed_data`.

`input.pcap` is generated by `gen.py`; it carries zeroed checksums, hence
`-k none`.
