NFSv2 handle to name resolution.

RFC 1094 keeps the object's name in the request, and returns the object's
handle in the LOOKUP reply (`diropres`: status, handle, attributes); CREATE and
MKDIR return a handle the same way. Every later handle-only operation -
GETATTR, SETATTR, READLINK, READDIR, STATFS, READ - can only name its file if
that reply wrote the handle to name mapping.

The capture is a v2 LOOKUP of `cfile` and the reply carrying its handle, then a
READLINK and a SETATTR on that handle. Neither request carries a name, so the
`nfs.filename` in their records can only come from the mapping: it is empty
while the reply's handle is not stored, and reads `cfile` once it is. The LOOKUP
record's `nfs.hhash` pins the same thing from the other side - it is the handle
the reply returned.

Two more flows pin the guard rails around the mapping: a LOOKUP answered with
`accept_stat` GARBAGE_ARGS (no body, must not be flagged malformed), and a
LOOKUP whose 300 byte name is over the RFC 1094 bound - the LOOKUP is flagged,
and the SETATTR that later resolves that name from the map must not be.

`input.pcap` is generated by `gen.py`; it carries zeroed checksums, hence
`-k none`.
