Lua SMTP stale transaction handle
=================================

One SMTP session over a single flow carrying two complete emails, each
command in its own packet, so that the parser reaps transaction 0 (the
EHLO/MAIL FROM/RCPT TO/DATA of the first email) when the second `MAIL FROM`
opens transaction 1 - while the flow is still live and still inspected.

Two Lua detection scripts read a transaction through `suricata.smtp`:

* `stale-tx.lua` caches the handle taken from transaction 0 and, once
  a second transaction is the current one (which is the moment the
  parser freed transaction 0), reads it again. The accessors fail
  closed for a stale handle: the accessor check raises and aborts the
  run - the sandbox blocks `pcall`, so the script cannot catch it, and
  sid 1 never alerts. The engine logs the error ("tx no longer
  valid"), which is what the test asserts on. The read is gated on
  observing the second transaction, so the first read that can raise
  is the packet where transaction 0 was freed; what the logged string
  itself proves is scoped in the Expectations below.
* `fresh-tx.lua` reads through a handle taken from the transaction that is
  current right now (sid 2, pcap_cnt 8). This is the pin: it shows the
  library does run, so leg 1 cannot go quiet for the wrong reason.

Both scripts attach through detection rules (the `lua:` keyword); the
sibling `tests/lua-sbx-uaf-smtp-tx` exercises the same contract through the
lua **output** script's `log()` callback - a different, also legitimate
attachment mechanism, not interchangeable with this one.

A third rule, sid 3, is a plain match on the `DATA` command and is pinned at
pcap_cnt 13. It is not what frees transaction 0 - the parser frees it
when the second `MAIL FROM` opens transaction 1, with or without this
rule - but it does record that the parser saw the first `DATA`
exchange, so a fixture change that moves transaction 0's lifecycle
shows up here as a sid 3 pin failure rather than as an unexplained
failure of leg 1.

Expectations:

* With the fix for issue #9120 all legs pass: the stale handle is refused
  (the accessor check raises and the error is logged) and the live one still
  reads.
* On engine main before that change, leg 1 fails
  (the shell check finds no "tx no longer valid" line): the accessor
  dereferences the freed transaction and returns a value, so it can never
  report an error. The run itself exits 0 - a non-instrumented build has no
  visible symptom, the symptom is precisely that the read succeeds.

What the test proves, and what it does not: a green leg 1 proves the
accessor **failed closed** (a stale handle raises and is logged) - a
currentness-style guard (the handle is not the transaction under
inspection) would log the same string and pass. The use-after-free
evidence itself is the asan leg of the CI matrix, where the unfixed
engine dereferences freed memory instead of logging nothing.

`input.pcap` is generated by `gen_input_pcap.py` (scapy) and committed; the
script is kept for provenance and is not run from the test (the CI image has
no scapy/tshark, and a setup failure scores the test as failed). Each data
packet acknowledges everything the peer has sent, so the capture is an
ordinary dialogue rather than a run of un-acknowledged segments.
