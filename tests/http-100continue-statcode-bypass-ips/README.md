# http-100continue-statcode-bypass-ips

IPS-mode (`--simulate-ips`) end-to-end reproducer for **both**
100-Continue stat_code deviations, with a plain, small 100-continue
exchange — no header-size trigger, no ACK dependency.

Sibling of `http-100continue-statcode-bypass` (NIDS mode; there the
client's normal auto-ACKs of the 100 line and the empty line give each
of them its own parse/detect cycle, so the same plain exchange
reproduces the deviation identically).

## Why IPS mode reproduces the full deviation

In inline mode the stream engine processes each packet's own direction
immediately (`UPDATE_DIR_PACKET` in `StreamTcpReassembleHandleSegment`);
in the default IDS mode it defers (`UPDATE_DIR_OPPOSING`, triggered by
the opposing ACK). In IPS mode every packet gets its own
parse/detect cycle, which is exactly the boundary the deviation needs:

1. `100 Continue` line (own packet): response tx at HEADERS (C > P) —
   the prefilter's final run alerts on the "100" stat_code buffer and
   stores the per-tx `detect_progress` bookkeeping.
2. Empty line (own packet): the htp parser
   rewinds the SAME tx (HEADERS -> LINE, status number kept at 100,
   headers cleared). The non-terminal re-run at LINE matches the stale
   "100" buffer again — **second alert (FP double alert)**. The rewind
   resets neither the buffer nor `detect_progress`.
3. Final `200 OK` (own packet): the tx reaches COMPLETE (C > P), but
   the tx-level prefilter bookkeeping sees `detect_progress >
   tx_min_progress` and skips the tx — **the final 200's stat_code is
   never inspected (FN bypass)**.

## Expected results (flow B, `10.0.0.3`)

| observation                          | flow A | flow B (expected) | on a pre-fix build |
|--------------------------------------|--------|-------------------|--------------------|
| `http.stat_code; content:"200"` (mpm, sid 1001) | 1 | 1 | **0 (bypassed)** |
| same rule without MPM (pcre, sid 1003)          | 1 | 1 | **0 (bypassed)** |
| `http.stat_code; content:"100"` (sid 1002) on the 100 line | 0 | 1 | **2 (double alert)** |
| http log status for the final response | 200  | 200 | 200 |

**Scope (pinned by sids 1004-1006, green even on a pre-fix build):**
same scope controls as the NIDS sibling — flow B's final 200 carries a
distinctive response header (`X-Test: finalmarker`) and body
(`hello200`); the rules on `http.header` (1004) and
`http.response_body` (1005) fire on the final 200 as usual, and the
request-side rule on `http.host` (1006) fires on the request. The
affected set is the response-line buffer family (stat_code,
stat_msg, response_line and the protocol token; the sibling tests
reproduce the same deviation for stat_msg and response_line).

The test is RED against a pre-fix build on exactly the flow-B
stat_code checks (1001/1003 -> 0, 1002 -> 2) and GREEN once the fix
(new response tx / progress reset on 100-continue) lands.

## Real-world client and server behaviour (severity)

Flow B is a standard, spec-compliant exchange - no attacker-controlled
or misconfigured party is involved:

- **Client:** textbook RFC 7231 Expect: 100-continue - sends the POST
  headers with `Expect: 100-continue` and waits for the `100` before
  sending the body (spec-legal; the normal pattern for large uploads).
- **Server:** standard 100-continue handling - replies with a bare
  `100 Continue` status line (no headers; the shape Apache/nginx/Java
  and similar send) before the final response.
- **Consequence:** the deviation is reachable with a **legitimate
  client and a legitimate server** (ordinary traffic), not the
  "evil client + evil server" class. IPS mode adds no dependency on
  ACK timing at all (per-packet processing), so the same exchange
  reproduces it regardless of the client's ACKs.

## Notes

- `args: [--simulate-ips]` in `test.yaml` runs suricata in IPS
  simulation mode.
- Regular pcap, scapy-generated by `writepcap.py`, byte-identical to
  the script's output.
- tshark dissects both flows as HTTP overall; note that tshark (4.6.4)
  does not HTTP-dissect flow B's request and 100-line packets because
  the 100 response spans two packets (the 100 line and the empty line
  are separate) - a dissector quirk, verified against a control pcap
  with the 100 self-contained in one packet (which tshark dissects
  fully, request included). Suricata parses the pcap correctly, as the
  test results show.
