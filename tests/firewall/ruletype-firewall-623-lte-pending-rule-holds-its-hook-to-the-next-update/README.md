An LTE rule pending above the transaction holds its hook until the transaction gets there
=========================================================================================

sid 110 is hooked `less-than` at `request_headers` with an `http.host` pattern that never
arrives. sid 120 is a listed rule of a higher id at that same hook, and its pattern *is* in
frame 4. The paragraph in `doc/userguide/firewall/firewall-design.rst` about this makes two
claims - that nothing decides while the transaction has not reached the pending rule's hook,
and that a rule of a higher id at that hook is inspected once it is reached.
`ruletype-firewall-616` pins the second one; it says nothing about the first, because none of
its filters name a packet. This test pins the first, and the timeline.

| packet | tx progress at that update | what the filters assert | why |
|--|--|--|--|
| 4 | `request_started`, below the hook of both rules | no alert of any kind | the walk has not reached either rule's hook; sid 110 is pending and its presence defers the hook's default, so `2201001` cannot drop the request here either |
| 6 | `request_headers`, the header block closes | sid 120 `blocked` at `http:request_headers` | the transaction is now at the hook, the walk inspects the listed rules in iid order and 120's `drop:flow` decides |
| any | - | sid 110 never alerts | its no-match is not a decision; it is simply still in the running when 120's action ends the flow |
| end | - | flow `drop` | 120's action, not a default policy |

Measured, not assumed
---------------------

* `DetectFwLtePendingRule()` forced to return `NULL` (no pending rule ever found): **this
  test fails** on filter 1 - an alert appears on frame 4, `2201001 blocked` at
  `http:request_started` - and on filter 3. `616` fails under the same mutant too, on its
  filter 2, because the flow ends at frame 4 and 120 never gets inspected. So this mutant is
  caught by both; it is the packet that this test adds, not the sensitivity.
* Making the retirement branch at the bound unconditional (`detect-engine-prefilter.c`,
  `tx_progress == bound && tx_progress < tx_end_state`): no observable change. That branch
  handles a group that is *in* the list at `bound + 1`; neither rule here takes it.
* Changing `tx_progress <= s->app_progress_hook` to `<` in the partial-match arm of the walk
  (`src/detect.c:3060`): no observable change, and a `breakpoint` on that line never fires
  for this fixture - so this test does not cover that arm. An earlier version of this test
  was written to cover it and was wrong: giving 110 a second content on the same buffer does
  not produce an in-list partial match, and hooking it at `<request_line` instead is refused
  when the ruleset loads (`engine progress value 2 doesn't match hook 1`,
  `SigValidateCheckBuffers()`), because `http.host` belongs to `request_headers`.
* main `4badfd13f`: same events on the same packets, so both halves of the paragraph are
  preserved behaviour rather than branch behaviour.

input.pcap is generated by `gen_pcap.py`. Frame 4 carries the request line and one header
without the closing CRLF, which is what leaves the transaction at `request_started` with the
header block open; frame 6 closes it. Validate with `tshark -r input.pcap -Y http`.
