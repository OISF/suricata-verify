# ruletype-firewall-232-lte-split-request-line

Regression test: a request line split over two TCP segments must not be
treated as a definitive no-match while the line (and with it the
`http_uri`/`http_method`/... buffers) can still complete at the rule's own
hook state.

## Scenario

`accept:flow http1:<request_line ... (http.uri; content:"/index";)`.

The pcap (generated by `generate-pcap.py`, see `input.pcap`) is an HTTP GET
whose request line is split over two TCP segments:

* segment 1: `GET /ind` — the line is incomplete; the HTP progress is at
  `request_line` (LINE), and the `http_uri` buffer is still empty (there is
  no partial request-line inspection; the line fields are only set once the
  line completes)
* segment 2: `ex HTTP/1.1` + headers — the line completes, still at LINE
  progress (the progress only moves to `request_headers` when the line's
  CRLF is consumed), and the `http_uri` buffer becomes `/index`

On the first segment the line engine has no matching content yet, but the
line is incomplete, so the no match is provisional. When the second segment
completes the line the keyword matches and the `accept:flow` rule accepts the
flow.

## Expected

* 0 `firewall default app policy` drops.

If the empty-buffer no-match at `request_line` is treated as definitive
(CANT_MATCH), the LTE rule dies before the line completes and the flow is
dropped by the default app policy even though the completed line matches.
