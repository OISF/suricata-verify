# ruletype-firewall-246-lte-file-keywords-segmented

Validation of the filehandler `app_stream` registrations toclient:
`file.magic`, the `files` multi-buffer (the `filename` keyword) and
`file.name`. The rules are ordered `file.magic` first; since the first
matching rule accepts the flow, only sid:211 is evaluated on flow A. The
other two registrations stay covered by the no-match decision on flow B.
Complements test 238, which covers `file.data` (via `http.response_body`)
at the same progress value.

## Scenario

Three LTE rules, one per buffer, all with hook `http1:<response_body`:

* sid:211 `file.magic; filemagic:"PNG"`
* sid:212 `filename:png` (the file extension)
* sid:213 `file.name; content:"match.png"`

Pcap (generated by `generate-pcap.py`) carries two HTTP file downloads. The
file data arrives in two segments (4 + 30 bytes): on the first body pass the
file has just started (4 bytes) so the magic is not determined yet - the file
starts only with the first body byte and the magic is computed when the file
completes. The no-match of that first body pass is PROVISIONAL (the
filehandler buffers are streaming: a file may still start and grow at the
engine's progress) and must not be converted to CANT_MATCH.

* A (port 49240): downloads "match.png" (a valid PNG) - the magic keyword
  matches when the file completes and the flow is accepted; the name keywords
  at the same hook are not evaluated (first match accepts).
* B (port 49241): downloads "other.txt" (text content) - no keyword matches;
  the engines' own eof CANT_MATCH drops the flow once - streaming defers the
  decision, it never waives the drop.

The toserver accept:hook shield (sids 701-706) keeps the toserver direction
from adjudicating the flow before the toclient direction does.

## Expected

exactly 1 `firewall default app policy` drop (flow B).
