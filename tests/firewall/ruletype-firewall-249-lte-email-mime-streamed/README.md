# ruletype-firewall-249-lte-email-mime-streamed

Per-buffer validation of the eight `email.*` `app_stream` registrations:
`email.from`, `email.subject`, `email.to`, `email.cc`, `email.date`,
`email.message_id`, `email.x_mailer` and `email.body_md5`.

## Scenario

Eight LTE rules, one per buffer, all with hook `smtp:<request_data`:

* sid:211 `email.from; content:"alice"`
* sid:212 `email.subject; content:"marker subject A"`
* sid:213 `email.to; content:"bob@example.com"`
* sid:214 `email.cc; content:"cc@example.com"`
* sid:215 `email.date; content:"01 Jan 2024"`
* sid:216 `email.message_id; content:"midA@ex.com"`
* sid:217 `email.x_mailer; content:"MailerA/1.0"`
* sid:218 `email.body_md5; content:"834ce629a80f4271126e63f548dc0029"` (the
  md5 of body "bodyA")

Pcap (generated by `generate-pcap.py`) carries 16 SMTP sessions. The MIME
headers stream in during DATA (progress request_data): the first MIME packet
carries only the From line, the remaining headers and the body arrive in the
second packet. On the first DATA pass the other email buffers are empty -
their no-matches there are PROVISIONAL (the buffers are streaming: the MIME
keeps streaming at their registered progress) and must not be converted to
CANT_MATCH.

* A1-A8 (ports 49270-49277): the full MIME carries all marker values;
  `email.from` matches on the first pass and the remaining keywords match
  when the second packet is parsed (the body_md5 once the body is complete);
  the flows are accepted.
* B1-B8 (ports 49278-49285): different sender, recipient, cc, date, subject,
  message-id, x-mailer and body; no keyword matches; each flow is dropped
  once when the mail completes - the engines' own eof CANT_MATCH rejects the
  rules; streaming defers the decision, it never waives the drop.

## Expected

exactly 8 `firewall default app policy` drops (one per B flow).
