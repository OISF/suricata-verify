# ruletype-firewall-243-lte-http1-response-line-keywords

Per-buffer validation of the remaining response-line (LINE) `app_stream`
registrations toclient: `http.response_line`, `http.stat_msg` and
`http.protocol`. Complements test 236, which covers `http.stat_code` at the
same progress value.

## Scenario

Three LTE rules, one per buffer, all with hook `http1:<response_line`:

* sid:211 `http.response_line; content:"200 OK"`
* sid:212 `http.stat_msg; content:"OK"`
* sid:213 `http.protocol; content:"HTTP/1.1"`

Pcap (generated by `generate-pcap.py`) carries 6 flows, each with a plain GET
request and the status line split over two TCP segments:

* A1-A3 (ports 49210-49212): the line completes into "HTTP/1.1 200 OK" - all
  three keywords match; the flows are accepted.
* B1-B3 (ports 49213-49215): the line completes into "HTTP/1.0 503 Gone" -
  none of the three keywords matches; each flow is dropped once.

While the status line is incomplete (first segment) the HTP response progress
is at response_line and the line buffers are empty - there is no partial
response-line inspection, the line fields are only set once the line
completes. The empty-buffer no match of the first segment is therefore
PROVISIONAL at the rule's own hook state and must not be converted to
CANT_MATCH (all three buffers are streaming). Each B flow is rejected by the
engines' own eof CANT_MATCH; streaming defers the decision, it never waives
the drop.

The toserver accept:hook shield (sids 701-706) keeps the toserver direction
from adjudicating the flow before the toclient direction does.

## Expected

exactly 3 `firewall default app policy` drops (one per B flow).
