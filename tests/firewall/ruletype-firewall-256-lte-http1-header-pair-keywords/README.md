# ruletype-firewall-256-lte-http1-header-pair-keywords

Per-buffer validation of the http1 `app_stream` registrations of the
`http.request_header` and `http.response_header` multi-buffers (the
`http.request_header` / `http.response_header` keywords: the header
name+value pairs populate line by line during the HEADERS progress).

## Scenario

Two LTE rules:

* sid:211 `accept:flow http1:<request_headers (http.request_header; content:"X-Marker: valA"; ...)` (tosever)
* sid:212 `accept:flow http1:<response_headers (http.response_header; content:"X-RespMark: valA"; ...)` (toclient)

Pcap (generated by `generate-pcap.py`) carries three HTTP flows:

* A1/A2 (ports 49350-49351): the request header "X-Marker: valA" arrives in
  the second request segment and the response header "X-RespMark: valA" in
  the second response segment. On the first segment of each side the
  multi-buffers do not yet contain the marker header - the no-match there is
  PROVISIONAL (the multi-buffers are streaming) and must not be converted to
  CANT_MATCH; the keywords match when the second segment is parsed and both
  flows are accepted.
* B (port 49352): "valB" on both sides; no keyword matches; the toserver
  side is dropped once by the engine's own eof CANT_MATCH (the toclient side
  is masked by the flow drop) - the deferral never waives the drop.

## Expected

exactly 1 `firewall default app policy` drop (flow B).
