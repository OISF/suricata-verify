# ruletype-firewall-244-lte-http1-response-header-keywords

Per-buffer validation of the remaining response-header (HEADERS)
`app_stream` registrations toclient: `http.cookie` (Set-Cookie),
`http.header_names` and `http.start`. Complements test 237, which covers
`http.header` toclient at the same progress value.

## Scenario

Three LTE rules, one per buffer, all with hook `http1:<response_headers`:

* sid:211 `http.cookie; content:"sct=cookieA"`
* sid:212 `http.header_names; content:"X-RespA"`
* sid:213 `http.start; content:"X-StartR: s1"`

Pcap (generated by `generate-pcap.py`) carries 6 flows. The response line
plus the Server header complete in the first segment (progress moves to
response_headers); the discriminating headers arrive in the second segment.

* A1-A3 (ports 49220-49222): segment 2 carries
  "Set-Cookie: sct=cookieA", "X-RespA: r1" and "X-StartR: s1"; the flows are
  accepted.
* B1-B3 (ports 49223-49225): segment 2 carries "Set-Cookie:
  sct=cookieB", "X-RespB: r2" and "X-StartQ: s2" - none of the three
  keywords matches; each flow is dropped once.

The header buffers populate line by line during the HEADERS progress, so the
no-match of the first segment (before the second segment's headers are
parsed) is PROVISIONAL at the rule's own hook state and must not be converted
to CANT_MATCH (all three buffers are streaming). Each B flow is rejected by
the engines' own eof CANT_MATCH; streaming defers the decision, it never
waives the drop.

The toserver accept:hook shield (sids 701-706) keeps the toserver direction
from adjudicating the flow before the toclient direction does.

## Expected

exactly 3 `firewall default app policy` drops (one per B flow).
