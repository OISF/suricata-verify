# ruletype-firewall-241-lte-http1-request-line-keywords

Per-buffer validation of the remaining request-line (LINE) `app_stream`
registrations: `http.method`, `http.request_line`, `http_raw_uri` and
`http.protocol` (tosever). Complements test 233, which covers `http.uri` at
the same progress value.

## Scenario

Four LTE rules, one per buffer, all with hook `http1:<request_line`:

* sid:211 `http.method; content:"GET"`
* sid:212 `http.request_line; content:"GET /"`
* sid:213 `content:"/index"; http_raw_uri`
* sid:214 `http.protocol; content:"HTTP/1.1"`

Pcap (generated by `generate-pcap.py`) carries 8 flows, each with the request
line split over two TCP segments:

* A1-A4 (ports 49170-49173): the line completes into "GET /index HTTP/1.1" -
  every one of the four keywords matches; the flows are accepted.
* B1-B4 (ports 49174-49177): the line completes into "PATCH /p HTTP/1.0",
  "PUT /upload HTTP/1.0", "DELETE /x HTTP/1.0" and "POST /submit HTTP/1.0" -
  none of the four keywords matches; each flow is dropped once.

While the line is incomplete (first segment) the HTP progress is at
request_line and the line buffers are empty - there is no partial request-line
inspection, the line fields are only set once the line completes. The
empty-buffer no match of the first segment is therefore PROVISIONAL at the
rule's own hook state and must not be converted to CANT_MATCH (all four
buffers are streaming: their data still arrives at their registered progress).
Each B flow is rejected by the engines' own eof CANT_MATCH when the completed
line never matches; streaming defers the decision, it never waives the drop.

## Expected

exactly 4 `firewall default app policy` drops (one per B flow).
