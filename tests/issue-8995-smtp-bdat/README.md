# Description

A syntactically valid, non-empty BDAT command is rejected before the client
sends any of its advertised chunk octets. Suricata must leave BDAT data mode
when it sees the error reply so the following RSET, envelope, DATA command,
and EICAR message remain synchronized and inspected.

# PCAP

The pcap is a live capture of a real Postfix server, generated by the email
sandbox scenario `bdat-rejected-before-chunk` in `smtp-oddseq.py`. The sandbox's
test-only Postfix `command_filter` rewrites this exact BDAT command to an
envelope-less DATA command internally, making Postfix send an immediate `503`;
the command captured on the wire remains a valid BDAT.

The important sequence is:

```
---> EHLO client.example.com
<--- 250-PIPELINING
<--- 250 CHUNKING
---> BDAT 1000000 LAST
<--- 503 5.5.1 Error: need RCPT command
---> RSET
<--- 250 2.0.0 Ok

---> MAIL FROM:<alice@example.com>
<--- 250 2.1.0 Ok
---> RCPT TO:<bob@example.com>
<--- 250 2.1.5 Ok
---> DATA
<--- 354 End data with <CR><LF>.<CR><LF>
---> (message containing the EICAR test string)
---> .
<--- 250 2.0.0 Ok: queued as <id>
---> QUIT
<--- 221 2.0.0 Bye
```

The test checks that RSET completes the abandoned BDAT attempt, the delivered
message is parsed in a fresh transaction, and a `file.data` rule alerts on the
EICAR marker. Without rejected-BDAT recovery, Suricata remains in BDAT data
mode and consumes every later client command and message byte as part of the
missing million-octet chunk.
